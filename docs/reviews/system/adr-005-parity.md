## Section 4 — Findings for Ship-4 spec

Ship-4's likely scope is **S08 case-management state-progression half** (per [`docs/ships/ship-4.md`](../../ships/ship-4.md) §1 — draft spec already opened, mechanical sections pre-filled, user-owned §6 sub-decisions still TODO). The §S positions Ship-4 will first-exercise are **§S4 + §S5 + §S6 Rules 1 & 5**. §S1 is "mechanism present, not exercised" per Ship-4 spec sub-decision 6.

The Ship-4 spec must include the following sub-decisions before code begins:

1. **Case-as-subject vs household-as-subject binding (§S5 + §S6 R1)**. ADR-005 §S5 lists `case_management` with states *Open → interact → refer/transfer → resolve → close → reopen*; these are case-as-subject states, not household-as-subject states. ADR-008 §S1 reserved [`subject_ref.type = "process"`](../../adrs/adr-008-envelope-reference-fields.md#s1-subject-ref-envelope-field) for exactly this kind of aggregate; Ship-4 must pick: (a) `case/v1` events carry `subject_ref.type = "subject"` of the household + a payload `case_id`, with the case-as-aggregate tracked at projection-replay time only, or (b) `case/v1` events carry `subject_ref.type = "process"` (or a new `case` enum value) with the case-as-subject identified by a UUID. ADR-008's reserved-`process` was opened pre-Ship-1 for this moment. **Highest-signal Ship-4 sub-decision** — locks the subject-binding contract for every future state-machine pattern.

2. **JAR-bundled pattern format (§S5)**. §S5 says *"Pattern definitions are synced to devices as part of the atomic configuration package (ADR-4 S6)"*. Ship-4's slice is server-only, so device-sync defers to a Ship-4b. The on-server pattern file format (named states, valid transitions, shape→pattern bindings) lands the moment Ship-4 commits a pattern fixture. JSON or YAML; deployer-authoring surface defers to FP-012. **No Flyway migration needed** — pattern fixture is a JAR resource, not a DB table.

3. **§S2 readiness gap**. Ship-4 spec §2 declines to emit `transition_violation` (sub-decision 6 territory). §S2 ("flagged events excluded from state derivation") is therefore not exercised this Ship. Ship-4's case projection must NOT silently couple state derivation to flag-presence in a way that becomes hard to add later. Concretely: when [`ConflictDetector`](../../../server/src/main/java/dev/datarun/ship1/integrity/ConflictDetector.java) eventually emits `transition_violation`, the case projection must consult flag-state per event before folding. Ship-4 spec should record this as a forward-pointing observation; the Ship that lands the first state-machine flag (Ship-5 or later) authors the flag-aware exclusion path.

4. **Schema impact** — **none for §S4 / §S5 / §S6 R1+R5 in Ship-4**. Case-state lives in `case/v1` payload (per Ship-4 spec §2 — *"`type=capture` envelopes with `state` in payload"*); the [`events`](../../../server/src/main/resources/db/migration/V1__ship1_schema.sql) table accommodates new `shape_ref` values trivially. **No Flyway migration required for the ADR-005 first exercise.** This is the lowest-cost-to-defer §S surface — pattern infrastructure is JAR-resource + projection-replay, not schema. Ship-4 inherits the [FP-002 (a)](../../flagged-positions.md#fp-002--subject_lifecycle-table-read-discipline-audit) "no projection cache; per-request replay" precedent at zero migration cost.

5. **Conflict with existing schema** — **none**. The `subject_lifecycle` table is absent from [`V1__ship1_schema.sql`](../../../server/src/main/resources/db/migration/V1__ship1_schema.sql) (verified at this walk; FP-002 close-out option (a) holds). The 6-value envelope `type` CHECK constraint accommodates `case/v1` events as `type=capture` with no migration. The `subject_type` CHECK constraint accepts `subject|actor|assignment|process`, which directly admits sub-decision (1)(b) above with no migration if Ship-4 picks `process`.

6. **§S5 Pattern Registry as PRIMITIVE × deployer-authoring surface (FP-012)**. Charter [Primitives](../../charter.md#primitives) already lists `pattern` as a platform-fixed primitive (citing [ADR-009 §S3](../../adrs/adr-009-platform-fixed-vs-deployer-configured.md)). Ship-4's JAR-bundled pattern fixture is consistent with the primitive's "platform-fixed, deployer-referenced" classification. The deployer-reference surface (instance-side per [ADR-009 §S1](../../adrs/adr-009-platform-fixed-vs-deployer-configured.md#s1-duality-rule-charter-invariant) duality) is parked at FP-012 alongside the deployer-shape surface. Ship-4 does not need to resolve FP-012 to land §S5 — only to declare that the resolution surface is unbuilt this Ship.

## Section 5 — Composition-rule drift signals

Pairs of §S positions where Ship-4 (or the next §S-exercising Ship) introduces an interaction ADR-005 did not pre-decide. Recorded conservatively — false positives are cheap.

- **SD-1: §S2 × existing event-replay projectors.** [`SubjectLifecycleProjector`](../../../server/src/main/java/dev/datarun/ship1/admin/SubjectLifecycleProjector.java) and [`ScopeResolver`](../../../server/src/main/java/dev/datarun/ship1/scope/ScopeResolver.java) fold events with no flag-status check. They are vacuously §S2-clean today only because no flag category currently targets `subjects_merged/v1`, `subject_split/v1`, `assignment_created/v1`, or `assignment_ended/v1`. The moment any flag (e.g., a future `domain_uniqueness_violation` on a merge, or an `identity_conflict` whose source is itself a merge) lands on these shapes, the projectors begin to silently violate §S2. ADR-005 did not pre-decide whether the lifecycle/scope projectors are "state-machine projections" subject to §S2 exclusion or "non-pattern projections" outside §S2's scope. **Action**: not a Ship-4 blocker (the consumed shapes remain flag-free in Ship-4); flag for the Ship that first emits a flag against any of these shapes.

- **SD-2: §S5 × FP-012 resolution shape.** Ship-4 lands the first JAR-bundled pattern fixture. FP-012 (deployer-authoring surface) when closed will need to lift patterns out of the JAR alongside shapes. ADR-005 §S5 says patterns are "synced to devices as part of the atomic configuration package" — but the wire format ([FP-013](../../flagged-positions.md#fp-013--config-package-wire-versioning-scheme)) is unbuilt. The pattern-package ↔ shape-package coupling (must they version together? can a pattern v1 reference shapes vN?) is not pre-decided in §S5 or in FP-012's gate. **Action**: Ship-4's pattern fixture format choice should record this question even if it doesn't answer it.

- **SD-3: §S7 × FP-008 root_cause trace.** §S7 (source-only flagging + chain traversal) and [FP-008](../../flagged-positions.md#fp-008--conflict_detected-payload-lacks-root_cause-trace-metadata) (root_cause trace metadata) are adjacent — both anticipate flags whose source-of-badness is distinct from the trigger. §S7's traversal walks `source_event_ref`; FP-008's `trigger_event_id` distinguishes "what got detected" from "what caused the detection." Ship-4 doesn't emit any non-self-trigger flags, so neither lands. The Ship that first emits a stale-reference flag (likely Ship-5/6 when merge/split flags interact with case captures) must close both together — the schema field landed by FP-008 path (c) is the seed for §S7's traversal. **Action**: cross-reference at the producing Ship; not a Ship-4 blocker.

- **SD-4: §S6 R1 × case-as-subject binding (Section 4 finding 1).** Rule 1 says "one subject-level pattern per activity." If Ship-4 picks `subject_ref.type = "subject"` (household) + payload `case_id`, then a household with multiple cases has multiple case-state machines bound at the *household* subject — which Rule 1 forbids unless the projection treats each `case_id` as a separate subject-level scope. ADR-005 §S6 R1 wording is ambiguous on whether "subject-level" tracks the envelope `subject_ref` or the pattern's logical subject. The reserved-`process` route (option (b) in finding 1) sidesteps the ambiguity entirely. **Action**: Ship-4 sub-decision 1 above resolves this; flagging the §S6 R1 wording-ambiguity in case the user picks (a).

- **SD-5: §S1 entry-guard discipline × FP-009 closure.** [FP-009](../../flagged-positions.md#fp-009--conflictdetector-field-name-coupling) closed at Ship-3 with the `ConflictDetector` entry-guard now keyed on shape-family prefix (`startsWith("household_observation/")` at [ConflictDetector.java:60](../../../server/src/main/java/dev/datarun/ship1/integrity/ConflictDetector.java)). When Ship-5+ first emits `transition_violation`, the detector grows a second entry-guard for pattern-bound shapes. Mechanical drift risk: a third entry-guard for the next category, then a fourth, then field-name-coupling re-emerges in different code. **Action**: when §S1 first exercises, the entry-guard layout should be made shape-driven (FP-012 c), not added to as a per-detector branch. Cross-reference FP-009 closure note.

## Section 6 — Verdict

1. **Conditional.** ADR-005 is ready to be exercised at Ship-4 with no supersession needed — the §S positions Ship-4 will first-exercise (§S4, §S5, §S6 Rules 1+5) require zero schema migration, zero envelope change, and fit within ADR-005's existing position language. Ship-4's slice is the smallest possible first-exercise of the ADR.
2. **Conditional points** (Ship-4 spec sub-decisions, not ADR-005-R supersession): (a) **case-as-subject binding** — `subject_ref.type` choice between `subject` (household + payload `case_id`) and `process` (case-as-aggregate); §S6 R1 wording-ambiguity favors `process`. (b) **JAR-bundled pattern format** — file format and on-server location for the `case_management` skeleton. (c) **§S2 readiness** — Ship-4 declines to emit `transition_violation`, so §S2 is not exercised; the Ship that first emits one (Ship-5+) carries the flag-aware exclusion sub-decision. None of (a)/(b)/(c) require a new ADR or an ADR-005-R; (a) and (b) are §6 sub-decisions inside Ship-4 spec.
3. **`exercised-violated` rows**: **none**. No §S of ADR-005 is contradicted by Ship-3 HEAD code. Ship-3 tag was correctly tagged with respect to ADR-005; this walk produces no retro-amendment finding.
