# Product / Domain Reality — Assigned Concerns

## C1-04 — Test topology too degenerate to validate scope reconstruction under real deployment conditions

**Issue**: Ships 1–3 test at a 2-actor, 2-village, 1:1 ratio. Real Phase 1 deployments have many actors per village, actors with overlapping historical assignments, and reassignments mid-campaign. The acceptance tests confirm correctness at minimum topology, not at real-world topology.

**Domain reality**: The Constraints doc describes tens of thousands of field workers and millions of records. The scenarios (S03, S09, S20) describe coordinated campaigns where many CHVs operate in overlapping areas with assignment changes mid-campaign. None of this complexity is exercised. The behavioral pattern P04 (Responsibility Binding) requires that reassignment is handled correctly — this claim is untested beyond a trivial case.

**Risk if ignored**: `ScopeResolver` correctness under real assignment complexity is assumed but unverified. When a Ship with real assignment complexity lands (S09-related), correctness gaps surface under live data.

**Action**:
- *Now*: Add an acceptance test with 3+ actors, 3+ villages, and at least one actor with overlapping historical assignments (assigned to V1 then V2 then back to V1). Assert scope reconstruction is correct at each temporal slice.
- *Later*: Use this topology as the standard test base for any future scope-dependent Ship.

**Reversibility**: High. Test addition; no code change required if implementation is correct.

## C3-04 — Config delivery wire format for shape deprecation status is undefined

**Issue**: W-7 confirms that v1 deprecated events are accepted and stored verbatim (correct). But the mechanism by which field devices *know* v1 is deprecated is unspecified. `/api/sync/config` presumably delivers shape status, but the response format for "deprecated" vs "current" vs "unknown" is not defined (FP-013 dependency).

**Domain reality**: The Constraints doc states that field workers can be offline for hours to days. P11 (Shape Definition and Evolution) requires that old records remain valid under the shape that was current when captured. But it also implies that field devices should not generate new records under deprecated shapes if they have connectivity. Without a deprecation signal in the config response, a device that syncs successfully after Ship-3 will continue generating v1 events — not because it is offline, but because it was never told v1 is deprecated.

**Risk if ignored**: v1 events continue to be generated by field devices indefinitely after deprecation. Identity conflict detection (already broken for v2) would then have to handle three cases: v1-v1, v2-v2, v1-v2 — none of which are currently handled except v1-v1.

**Action**:
- *Now*: Specify the deprecation wire format in the config response schema. Minimally: `{shape_ref, status: "current"|"deprecated", deprecated_since}`.
- *Later*: Add to `ConfigController` response and to the `/api/sync/config` contract documentation.

**Reversibility**: Medium. Config response format change; requires client-side handling. But no stored events are affected.

## C2-02 — FP-006 attribution seam (corrective split author) undecided with downstream consequences

**Issue**: When a coordinator corrects an erroneous merge by splitting, who authors the `subject_split/v1` event? If the coordinator is the author (`actor_ref` = their UUID), the event looks like a deliberate operational split. If a system actor is the author, the human decision is invisible. ADR-008 §S2 defines `actor_ref` as the author — but "author" in a correction context is ambiguous.

**Domain reality**: P03 (Trustworthy Records, principle P3) requires that every action is traceable: who did what, when, under what role. A corrective split where the human decision-maker is invisible violates traceability. A corrective split that looks like an operational split is misleading to anyone reading the event stream for audit purposes. Both outcomes are wrong.

**Risk if ignored**: The first Ship that emits a corrective split will implicitly choose one option. That choice becomes a precedent. If S04 (corrections) and S08 (case management) both reference splits, downstream projections will reason about split authorship in ways that depend on whichever implicit choice was made first.

**Action**:
- *Now*: Resolve FP-006. The correct model is: `actor_ref` = the coordinator who initiated the correction; `shape_ref` = `subject_split/v1`; add a `correction_of` field in the payload referencing the original merge event UUID. This preserves traceability (human visible) and distinguishes corrective splits from operational splits (payload-level, not type-level).
- *Later*: Update the `subject_split/v1` schema to include the optional `correction_of` field.

**Reversibility**: Medium. Shape evolution (additive field) is non-breaking. Existing splits (none at Ship-3 close outside of test data) are unaffected.
